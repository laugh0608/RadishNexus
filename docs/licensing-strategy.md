# RadishNexus 许可与分发策略

状态：产品策略已确认，正式法律文本待专业复核

日期：2026-08-27

## 当前决定

RadishNexus 采用分层授权模式：

- 核心产品代码和项目自有文档：source-available，版权和授权权利由项目所有者保留；
- Plugin SDK、公共协议、兼容测试和示例：开放源码；
- 官方插件和社区插件：开放源码，具体许可证由组件明确声明；
- 第三方依赖和资产：继续遵循其各自许可证。

根 [LICENSE](../LICENSE) 以 Radish 家族既有的 source-available 边界为参考，并针对本项目增加了单独免费书面授权、无席位计费承诺以及独立开放组件的边界。该说明只是来源背景，正式权利义务始终以本仓库许可证和单独书面授权为准。

## 核心代码

根许可证不是开放源码许可证。除查看和学习外，默认不授予部署、运行、复制、修改、再分发、提供服务或商业使用权。

实际使用通过项目所有者单独签发的书面授权完成。书面授权可以免费，但必须明确授权对象、使用范围、期限和其他条件。

该模式的目标是：

- 保持核心产品代码和商业安排的控制权；
- 允许可信用户或组织在获得授权后免费自部署；
- 防止未经许可的复制、再分发和商业托管；
- 不通过用户席位数量建立收费或功能门槛。

## 免费授权与无席位限制

免费授权应遵守以下产品原则：

- 不按用户、成员、访客、频道、项目、文档、工单或插件数量收费；
- 不在产品中实现席位计数激活逻辑；
- 首期可以通过邮件、签署文件或离线自助流程签发，不依赖官方在线授权服务器；
- 授权可以按个人、组织或部署主体定义，但不按组织内部人数拆分；
- 产品中的存储、并发和速率配额属于实例管理员的运维设置，而不是许可证限制；
- 未来即使引入付费能力，也不应追溯改变已签发授权的明确权利。

授权模板的范围、期限、是否允许修改、是否允许内部再分发以及终止条件尚未冻结，应在首次对外授权前形成独立模板并接受专业法律审查。

## 评估和授权体验

source-available 边界不能让合法评估变成高摩擦人工流程。首次可运行版本发布前，应同时提供清楚的评估路径和授权申请说明。

产品要求：

- 评估者无需按成员数申报或获得席位 Token；
- 授权文件按个人、组织或实例主体签发，不包含成员数量字段；
- 自部署核心运行不要求持续联网检查许可证；
- 不以遥测、官方账号或官方云连接作为免费授权的前提；
- 完全离线环境可以导入并本地验证授权材料；
- 授权失效或格式错误时提供明确诊断，不删除、加密或扣留用户数据；
- 数据导出、备份和恢复不因授权状态成为不可执行操作。

可以评估两条路径：公开授予有限期非生产评估权，或提供无需人工等待的免费授权签发。具体法律文本、身份校验、有效期和撤销边界仍需专业复核，不能只通过产品文案替代许可证授权。

## SDK 和公共协议

为了降低插件开发和企业内部集成成本，以下内容原则上开放源码：

- Plugin Manifest schema；
- Host API 和事件协议定义；
- Go、Rust 和 TypeScript SDK；
- 兼容测试和打包工具；
- 最小示例插件；
- 公共 Webhook 和消息卡片协议。

当前优先候选许可证为 Apache License 2.0，因为它提供明确的版权和专利授权；是否所有 SDK 和插件统一使用 Apache-2.0，仍需在首次创建组件时冻结。

每个开放组件必须在自己的目录放置 `LICENSE` 或明确的 SPDX 标识。仅在根 README 声明“SDK 开源”不足以形成清晰授权。

## 插件

- 官方基础插件默认应采用 OSI 认可的开放源码许可证；
- 社区插件由作者选择许可证，但必须在包中声明；
- 插件商店可以同时容纳免费和付费插件；
- 付费插件可以按插件、实例或支持服务收费，不应依赖 RadishNexus 核心席位数；
- 插件依赖核心 Host API 不应使其自动受根 source-available 许可证约束，具体边界由开放 SDK 许可证和插件协议保证。

## 商业化候选

当前不急于冻结商业模式，长期收入可以来自：

- 部署、迁移和升级服务；
- 企业技术支持和响应保障；
- 托管服务；
- 高可用、灾备和合规方案；
- 付费插件；
- 插件市场服务；
- 定制开发和私有集成。

商业化不能破坏以下底线：已经授权的自部署实例不因新增成员失效，数据导出和备份恢复不成为席位门槛，核心产品不依赖官方云才能正常运行。

可移植 `.nexus` 上下文包不得默认携带 Secrets、第三方 Token 或仅对原实例有效的授权材料。导入后应单独恢复插件凭据并重新确认目标实例授权。

## 仓库许可证布局

预期布局示例：

```text
RadishNexus/
├── LICENSE                    # 核心 source-available
├── server/                    # 继承根许可证
├── apps/web/                  # 继承根许可证
├── sdk/
│   └── LICENSE                # 未来开放源码许可证
├── contracts/
│   └── LICENSE                # 未来开放源码许可证
└── plugins/
    └── jenkins/
        └── LICENSE            # 插件自己的开放源码许可证
```

如果未来拆分仓库，每个仓库必须自带完整许可证，不能依赖另一个仓库的说明。

## 外部贡献

- 核心代码贡献需要保证项目所有者拥有继续修改、发布和再许可所需权利；根许可证当前沿用 Radish 的广泛贡献授权表述。
- 在公开接受核心大规模贡献前，应评估 CLA、版权归属和贡献者知情程度。
- SDK 和开放插件可以采用 `inbound = outbound`，贡献以组件自身许可证进入。
- Issue 中的建议不应被默认解释为对第三方代码、设计或商业秘密的授权。

## 法律复核

当前许可证和策略是项目规划草案，不构成法律意见。首次公开仓库、签发使用授权、接受外部贡献、推出付费插件或建立公司主体前，应对许可证、贡献协议、商标和数据合规做专业复核。
