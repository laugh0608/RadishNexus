# RadishNexus 插件系统

状态：原则基线，运行时尚未冻结

日期：2026-08-27

## 目标

插件系统用于让外部系统连接器和独立扩展能力不必进入核心发布节奏，同时允许社区或组织开发自己的集成。

插件系统不是产品目标本身。任何插件基础设施投入都必须由至少一个明确场景验证，不能为了获得“可插件化”的架构标签提前实现完整市场、复杂沙箱或多语言 SDK。

## 收益判断

一个功能只有满足以下至少一项时，才优先考虑插件：

- 依赖外部系统，并且外部 API、版本和凭据生命周期独立；
- 不是所有部署都需要；
- 适合由第三方或私有团队维护；
- 需要独立安装、升级或禁用；
- 能通过稳定 Host API 完成，不需要绕过核心权限和事务；
- 插件化显著降低核心依赖或发布风险。

如果插件化导致更多跨边界事务、重复权限逻辑、难以调试的调用链或额外 UI 框架维护，则应优先作为内建模块。

## 初始分类

| 能力 | 初始归类 | 原因 |
|---|---|---|
| 用户、Workspace、权限 | 平台内核 | 所有模块和插件共同信任的边界 |
| 私聊、频道、消息 | 内建模块 | 高频实时核心路径，强依赖权限和搜索 |
| Decision | 内建模块 | 人工确认、证据和替代链必须由平台保证 |
| 工单 | 内建模块 | 与消息、文档和状态事务深度关联 |
| 文档 | 内建模块 | 协同、历史、离线和权限复杂 |
| Initiative、Component、Environment | 内建上下文 | 是跨插件共享的研发语义和所有权边界 |
| Playbook 与 Run | 后续内建模块 | 需要稳定关联频道、行动项、审计和复盘 |
| Jenkins | 外部插件 | 独立 API、凭据和版本生命周期 |
| GitLab/GitHub/Gitea | 外部插件 | 可选外部系统连接器 |
| AI 总结与语义检索 | 外部插件优先 | 模型、部署和数据策略差异大 |
| 通用通知 Webhook | 轻量内建扩展点 | 价值明确且实现成本低 |
| 组织私有审批规则 | 声明式自动化或插件 | 不应修改核心代码 |

## 递进式实现

### P0：内建扩展点

在没有通用插件运行时前，先提供：

- 版本化 Webhook；
- Bot 身份；
- Slash Command 注册；
- 消息卡片数据结构；
- 事件订阅接口；
- 受控 EntityLink 写入和 Activity 展示；
- 插件设置和 Secrets 抽象；
- 后台任务注册。

这些能力可以先由同仓库 Jenkins 集成调用，用于验证接口，而不是立即对外承诺稳定 SDK。

### P1：首个可安装 Jenkins 插件

Jenkins 插件至少验证：

- 安装、启用、禁用和升级；
- 实例配置和连接测试；
- API Token 安全存储；
- Webhook 接收和签名/来源校验；
- 构建事件转换为统一 CI Run；
- 消息卡片和项目页面扩展；
- 重新构建等高风险操作的权限和审计；
- 插件失败不会阻塞核心消息和工单事务。

只有 Jenkins 插件暴露出真实需求后，才补充对应通用能力。

### P2：公开 SDK

在 Host API 经过至少一个真实插件使用并完成版本迭代后，再发布开放源码 SDK、示例插件、兼容测试和插件打包工具。

### P3：生态能力

私有插件仓库、签名发布、兼容认证、插件市场和收益分配属于后续能力，不进入早期 MVP。

## 插件能力模型

插件必须通过 Manifest 声明需要的能力。建议的能力类别包括：

- `events.subscribe` / `events.publish`；
- `messages.create` / `message-cards.render`；
- `commands.register`；
- `settings.read`；
- `secrets.use`；
- `network.connect`；
- `jobs.schedule`；
- `entities.read` / `entities.link`；
- `decisions.suggest`，只允许创建待人确认的草案；
- `ui.project-page` / `ui.settings-page`；
- 具体外部操作权限，例如 `ci.runs.trigger`。

安装页面必须展示权限和网络范围。升级新增权限时必须重新由管理员批准。

## 运行模型候选

首版运行模型尚未冻结，按真实需求选择：

### 声明式插件

适合简单 Webhook 映射、消息卡片、表单和自动化。实现成本最低，应优先覆盖简单场景。

### WASM 插件

适合短时事件处理、校验、转换和命令逻辑。优点是隔离和跨语言，代价是 Host API、调试、资源限制和生态成熟度成本。

### 独立进程或 Sidecar

适合 Jenkins、AI、复杂企业系统等长连接或依赖丰富的插件。通过版本化 HTTP/gRPC 协议调用，隔离较好，但部署和故障诊断成本更高。

不得因为已经支持某一种运行模型，就强迫所有插件使用它。也不要求第一阶段同时实现三种模型。

## 数据边界

- 插件不能直接读取核心业务表；
- 插件通过 Host API 读取经过权限过滤的实体；
- 插件数据使用独立 PostgreSQL schema、独立数据库或平台提供的 namespaced KV/document storage；
- 插件迁移由 Plugin Manager 记录和执行；
- 卸载默认不立即删除数据，应提供禁用、保留和显式清理三个阶段；
- 备份必须包含插件版本、配置、数据和加密 Secrets 的恢复策略。

插件可以建议 EntityLink、Decision 草案和 Attention Item，但不能借此绕过核心模块的不变量。`Decision.accept`、生产 Environment 审批和 Deployment 事实确认属于独立高风险 Host API，不包含在通用实体写入权限中。

## UI 边界

首期优先提供低成本扩展点：

- 消息卡片 schema；
- 项目工具页；
- Nexus View 卡片和受控动作；
- 设置表单 schema；
- 命令和动作菜单。

复杂第三方 UI 优先运行在 sandboxed iframe 中。第三方插件不能直接向主 React DOM 注入任意 JavaScript。官方可信插件是否允许 React 组件级集成，在真实需求出现后单独决定。

## 版本和兼容性

插件包至少声明：

- plugin ID；
- plugin version；
- plugin API version；
- 最低和最高兼容宿主版本；
- 权限；
- 扩展点；
- 网络范围；
- 数据迁移版本；
- 包校验值和签名信息。

Host API 只对已发布稳定版本做兼容承诺。实验性接口必须显式标记，避免 SDK 过早冻结错误抽象。

## 安全与故障隔离

- 插件默认无权限；
- Secrets 只以引用或受控调用方式使用，普通 API 不返回明文；
- 网络访问按主机和协议限制；
- 后台任务有超时、并发和重试限制；
- Webhook 有幂等、重放保护和来源校验；
- 插件错误不能回滚已经提交的核心业务事务；
- 高风险外部动作需要独立 RBAC、二次确认和审计；
- AI 插件生成的总结、Decision 和状态更新只能作为带证据引用的草案；
- 开发环境可允许未签名插件，生产环境默认要求可信来源。

## 停止线

出现以下情况时，应停止扩充插件基础设施并回到具体业务验证：

- 尚无第二个真实插件，却开始设计完整市场；
- 为兼容多个语言 SDK 重复实现尚未稳定的 Host API；
- 插件需要直接查询核心数据库才能完成基本工作；
- 核心模块为了插件接口被拆成大量远程调用；
- 插件开发成本明显高于在核心中实现，并且没有独立演进或生态收益；
- 插件安全模型无法向管理员清楚解释。
