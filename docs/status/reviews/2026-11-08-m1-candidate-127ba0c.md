## 本机 OrbStack T03 验收

2026-11-08，所有者确认使用本机 OrbStack 限定隔离验收。宿主为 macOS 27.0.1 arm64、OrbStack 2.2.5、Docker 29.8.2（linux/arm64）和 Compose 5.5.0。HTTPS 由 curl 8.7.1 验证。本机 Chrome 156.0.8078.80 仅作版本登记。使用合成管理员和独立数据库 Secret，入口限于 `https://localhost:18443`。

首次执行 `database-roles` 失败。上一轮在 `umask 077` 下解包候选快照，operations 镜像内的初始化脚本及两份 SQL 权限变成 `0600`，导致运维账号无法读取。改用 `git archive 127ba0c | tar -xpf -` 保留归档权限，从同一 Git 快照重建两套镜像。以 operations 默认的非 root 用户核实三份文件均可读取，再用上表的新镜像 ID 复跑。

| --- | --- |
| 初始化与迁移 | PostgreSQL 和 pg_dump 均为 17.10。PostgreSQL TCP 就绪，`database-roles → migrate → bootstrap → app / caddy` 成功。逐条比对 25 条迁移记录的序号、名称和校验值，均与 `127ba0c` 一致 |

## 本机 OrbStack T06 与 T07 验收

2026-11-08 使用上表登记的 `127ba0c` 工件与两个隔离 Compose 配置。所有者确认本机标准为从摘流到恢复入口验收不超过 120 秒，停写前已确认的写入丢失 0 条。本轮使用 1 个 Workspace、2 个 Project（含 1 个受限项目）、3 个合成账号和 100 条消息，其中受限项目 60 条、共享项目 40 条。保留一条 Message → Thread → Decision → Ticket → Document 来源链、一条人工复核和两版文档。停写前同一成员有 2 条并发 SSE 连接。源数据库为 11,818,675 字节，备份 dump 为 347,905 字节。

| T06 检查 | 本机实测 |
| --- | --- |

| 空库恢复 | 源与恢复目标的 Compose project、容器、volume 和 PostgreSQL system identifier 均不同，使用独立 Secret。先为目标准备角色，再用匹配的 operations 恢复空库。正式命令报告恢复成功及 ACL 应用完成 |
| 数据与权限 | 40 张权威表的行数和 SHA-256 摘要逐表一致，112 条领域事件完整，重建后 11 条 Activity 均为版本 13 且摘要一致。目标的 Session、未兑换邀请和 OIDC 事务均为空。旧 Session 返回 401，重新登录后成员可读来源链、进行中的 Ticket 及第 2 版 Document，越权请求仍返回 404 |

## 目标宿主 T03、T06、T07 清单

每项在现场记录执行人、时间、候选身份、结果与脱敏证据位置。首次执行前由项目所有者确认目标宿主、部署负责人、数据责任人和访问范围，并记录维护窗口、代表性样本、可接受停机与可接受数据损失。所有下列项目的正式试用宿主状态均为**待执行**。 [试用准入判据](../../trial-support.md#准入与退出判据) · [停机升级手册](../../../deploy/upgrade-recovery.md)

### T03 环境与工件

- [ ] 记录目标 OS、CPU、Docker / Compose、PostgreSQL / pg_dump、Caddy、浏览器和 CLI 运行平台。核对 Git 完整 SHA、app / operations 镜像 ID 或交接 digest、CLI SHA-256、Compose / Caddy 生效配置校验值。存在升级路径时，登记所用旧工件及其 schema 与恢复工具。
- [ ] 核对源与恢复实例的 Compose project、网络、volume、端口和 Secret 来源。确认无端口冲突，Caddy 按核准范围监听，app / PostgreSQL 无宿主端口，可信代理为预期 `/32`。从允许的客户端以实例 CA 验证正式 HTTPS，并验证错误 CA 的连接失败。
- [ ] 用合成数据在新源实例按顺序执行 `database-roles → migrate → bootstrap → app / caddy`。核对 PostgreSQL TCP 就绪、完整 schema 025 history、`/health/ready`、正式 Web 入口和运行账号的实际权限。检查 app 无 DDL、history 修改与既有审计改写权，backup 无业务表写权。 [身份拆分手册](../../../deploy/database-roles.md#新实例与独立恢复目标)

### T06 可恢复性

- [ ] 在同一候选的源实例生成可重建协作数据，记录最后确认的写入与在途请求。摘流后停止 app 及其他写入源，确认 SSE 关闭且无在途写事务。用专用 backup 身份生成归档，登记备份时点、schema / 工具版本及归档校验值。
- [ ] 核对独立目标的 Compose project、数据库容器、volume 与 PostgreSQL system identifier。目标使用独立 Secret，先执行 `database-roles`，在尚未 bootstrap / migrate 的空目标用匹配的 operations 执行 `restore`。记录恢复、Activity 重建和 ACL 重施结果。若恢复失败，保持目标隔离并按手册诊断。
- [ ] 逐项比对备份时点的权威表、成员权限、Decision → Ticket → Document 来源与审计 / receipt 摘要，核对 Activity 13。验证旧 Session 失效，重新登录后权限符合预期，并用同一请求精确重试复核 receipt。准备开放时记录唯一可写实例及其身份。
- [ ] 如首批范围包含从 024 升级，另在获准的隔离副本中核对旧工件恢复、DDL 失败后的 history 保持、显式续迁到 025、原管理员凭据轮换和 ACL。按 ADR-0043 矩阵逐项登记证据，独立操作者 U27 继续保留待验证。 [失败恢复矩阵](../../adr/0043-single-host-upgrade-failure-recovery.md) · [旧实例切换](../../../deploy/database-roles.md#旧实例停写切换)

### T07 数据取舍与测量

- [ ] 测量前记录样本规模及分布，包括 Workspace、Project、消息、事件、文档版本、数据库与归档大小、并发连接和多标签页。记录部署负责人确认的停机上限、数据责任人确认的数据损失上限，以及代表性样本的适用范围。
- [ ] 同一轮记录摘流开始、最后成功写入、确认停写、备份开始与结束、恢复开始与结束、Activity 可用、正式入口验收和获准重新开放的时间。分别报告停写、备份、恢复含重建以及端到端不可用的耗时。若没有单独的重建测量，登记为包含在恢复耗时中。
- [ ] 按备份点核对最后已确认写入，列明备份后写入、未决请求和观察到的恢复数据缺口。部署负责人和数据责任人分别比对实测停机与数据损失，未达到约定值时登记原因、处理决定和复验项。
