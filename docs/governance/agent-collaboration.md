# Agent 协作规范

本文件解释 RadishNexus 中人类与自动化 Agent 如何共同完成可审查的工作。具体可执行规则以根目录 [AGENTS.md](../../AGENTS.md) 为准。

## 开始任务

Agent 在修改前应：

1. 阅读根协作规则和与任务直接相关的真相源；
2. 检查工作区状态，区分既有改动与本次任务；
3. 明确用户要求的是分析、诊断还是实施；
4. 找到最小可验证范围，避免顺手扩张到未授权目标；
5. 对可能变化的外部事实使用权威来源核验。

读取和分析不等于获得远端写入、发布、部署、删除、提交或推送权限。需要改变外部状态时，应在动作前取得明确授权。

## 实施边界

- 优先修改真相源，再更新派生说明和自动化契约。
- 保留用户已有改动，不重置、不覆盖、不用生成器清空手写内容。
- 通用规则应表达不变量和判定条件，不绑定某个 Agent、编辑器或单次会话。
- 不以“兄弟项目这样做”为充分理由；每项约束必须能解释其对 RadishNexus 的价值。
- 新依赖、网络服务、数据库、容器和长驻进程需要明确必要性，并遵守仓库授权要求。
- 生成代码、迁移、协议和配置都必须能追溯到来源与生成命令。

## 产品语义红线

Agent 不能为了实现便利而静默改变以下含义：

- Project、Initiative、Component、Repository、Environment 各自承担不同职责；
- CI Run 记录构建执行，Deployment 记录向环境投放的事实；
- Decision 是包含问题、理由、证据和替代关系的一等对象；
- EntityLink 必须记录来源，Activity 是权限过滤后的事件投影；
- 私密消息、文档、搜索、通知、引用、导出和 AI 上下文都必须服从目标对象权限；
- 插件默认无权限，高风险写操作需要确认、审计和幂等保护；
- 自部署能力不能用席位数量作为授权或功能门槛。

如果实现要求改变这些语义，应暂停编码并先提出决策变更或 ADR。

## 验证与证据

验证应与风险成比例，并同时覆盖成功路径和关键失败路径：

- 文档/治理变更：运行 `./scripts/check-repo.sh`，检查链接、契约和差异；
- Go：格式化、单元/集成测试、静态检查；
- React/TypeScript：类型检查、测试、构建，以及关键交互和可访问性验证；
- Rust：格式化、Clippy、测试；
- Flutter：格式化、分析、测试；
- 权限、Webhook、插件和部署：补充越权、重复、重放、超时和恢复测试。

不能执行的验证要明确说明原因和残余风险，不得把“未运行”写成“通过”。

## 交接要求

最终交接至少包括：

- 结果与用户可感知的变化；
- 修改的关键文件；
- 实际运行的验证及结果；
- 尚未完成或需外部授权的事项；
- 有价值的下一步，但不替用户执行未授权动作。

只有用户明确要求时才提交、推送、创建 PR、应用 Ruleset、部署或发布。提交信息不得添加 AI 共同作者。
