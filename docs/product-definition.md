# RadishNexus 产品定义

状态：初始基线

日期：2026-08-27

## 一句话定义

RadishNexus 是面向研发团队的、自部署优先的沟通、协作与交付枢纽，把讨论、决策、工单、文档、构建、发布和复盘放进同一套可追溯上下文。

## 目标用户

首要用户是希望掌握数据和部署权、又不愿承担多个协作系统割裂成本的小型和中型研发团队。初始规模假设为单组织 5～200 人，但产品授权不得按人数设置功能限制。

主要使用者包括：

- 软件研发团队；
- 自建基础设施的技术团队；
- 小型公司和独立工作室；
- 对数据位置、离线环境或私有网络有要求的组织；
- 希望通过插件连接内部系统的团队。

## 核心问题

现有团队通常分别使用聊天、工单、文档和 CI/CD 工具。即使每个工具单独可用，跨系统上下文仍容易丢失：

- 需求决定停留在聊天记录里；
- 工单无法解释为什么这样设计；
- 文档与实际任务、构建状态脱节；
- 构建失败只能发送一条缺少上下文的通知；
- 发布完成后仍需人工拼接提交、工单和说明；
- 自部署产品常通过席位、企业认证或关键功能限制降低实际可用性。

RadishNexus 的目标不是复制多个成熟产品的全部功能，而是优先解决这些对象之间的转换、引用、权限、事件和追溯问题。

## 产品承诺

> 在一次讨论中，团队能够立即找到并操作相关工单、文档、构建、发布和结论；系统自部署时不因团队人数增加而失去基础能力。

## 核心对象

第一阶段围绕以下对象建立统一引用，精确职责以[领域模型](domain-model.md)为准：

- Workspace：组织级协作空间；
- Team：稳定的人员与责任边界；
- Project：协作导航和权限边界；
- Initiative：有目标和结束条件的阶段性工作；
- Component：长期维护的软件资产；
- Repository：外部代码库映射；
- Channel：公开或私密频道；
- Conversation：私聊或群聊；
- Message：消息及 Thread；
- Decision：问题、结论、理由、证据和替代关系；
- Ticket：需求、任务、缺陷、事故和改进项；
- Document：在线协作文档及版本；
- CI Run：构建或流水线运行；
- Environment：稳定部署目标及其保护策略；
- Deployment：某版本进入某 Environment 的事实；
- Plugin：外部能力和受控扩展。

每个对象原则上都应支持稳定 ID、权限、引用、评论或讨论、订阅、历史、搜索和审计，但具体能力按对象需要逐步实现，不追求形式上的完全一致。

Project、Initiative 和 Component 不得混为同一个“项目”概念：Project 解决协作入口和权限，Initiative 表达阶段目标，Component 表达长期软件资产。CI Run 与 Deployment 也必须分开，构建成功不自动等于已经部署。

## 核心工作流

### 从讨论到执行

消息或 Thread 可以提炼为 Decision 草案，也可以转换为工单，并保留原始讨论、创建者和时间的双向引用。Decision 经人确认后可以产生 Ticket；工单后续状态可以回写原讨论，但不能通过噪声通知淹没频道。

### 从执行到知识

工单可以关联设计文档、Decision 和操作手册；文档可以嵌入实时工单与 Decision 视图，而不是只保存静态链接。

### 从代码到交付

CI/CD 插件将 Repository 的外部构建和发布映射为统一 CI Run、Environment 与 Deployment 对象。失败构建可以关联 Component、工单、频道和事故流程；高风险操作必须通过权限、确认和审计控制。

### 从交付到复盘

发布说明和事故复盘可以基于关联的工单、讨论、构建和部署记录生成初稿，但任何自动生成内容必须可审阅、可修改和可追溯。

## 功能范围

### 沟通

- 私聊、群聊、公开频道和私密频道；
- Thread、表情回应、附件、@提醒、置顶和收藏；
- 未读、提及和 Attention Item 分离的统一入口；
- 消息转 Decision、转工单、引用文档和展示插件卡片；
- 全文搜索与基础审计。

### 决策

- 从 Message 或 Thread 建立 Proposed Decision；
- 记录问题、结论、理由、备选方案、证据和影响；
- 支持 Accepted、Rejected 和 Superseded；
- 提供待我决策、即将复核和已被替代视图；
- Decision 与 Ticket、Document、Component、CI Run 双向关联。

### 工单

- 需求、任务、缺陷等类型；
- 可配置状态、负责人、优先级、标签和截止时间；
- 列表和看板；
- 父子和依赖关系逐步提供；
- 与消息、Decision、文档、Component、CI Run 和 Deployment 双向关联。

### 文档

- 结构化在线编辑；
- 多人协作、评论和历史版本；
- 与工单、消息和构建对象互相引用；
- 导入、导出和备份；
- 离线编辑属于正式目标，但必须在在线协同模型和数据所有权稳定后分阶段交付。

### CI/CD

- 首期通过插件连接 Jenkins；
- 展示构建、阶段、状态、日志入口和测试结果；
- 明确区分 Component、Repository、CI Run、Environment 和 Deployment；
- 后续增加重新构建、取消、环境审批、部署和回滚；
- 所有外部写操作使用独立权限、明确确认和审计记录。

### 上下文与行动

- 所有重要对象提供 Current、Relations、Timeline 和 Actions 四类信息；
- EntityLink 记录关系类型、来源、创建者和时间；
- Attention Item 只承载需要用户行动的事项，不与未读通知混为一谈；
- Initiative 支持负责人、健康状态、周期更新和过期提醒；
- 后续 Playbook Run 将发布、故障和迁移过程连接到频道、工单、构建、部署和复盘。

## 产品原则

1. Web-first：先证明 Web 产品闭环，再启动客户端。
2. 自部署可运营：安装只是开始，升级、备份、恢复和诊断同样属于产品。
3. 无席位限制：授权、功能和部署不得依赖成员计数。
4. 上下文优先：先做好 Decision、EntityLink、Activity 和纵向工作流，再扩充单点功能数量。
5. 选择性插件化：插件必须降低耦合或创造生态价值，否则保持内建模块。
6. 数据可迁移：提供明确导出、备份和恢复边界，避免人为制造锁定。
7. 权限显式：跨模块引用不能绕过原对象权限。
8. 自动化可审阅：自动生成、触发和外部执行都必须可解释、可追溯和可关闭。
9. 交付事实分层：Repository、CI Run、Environment 和 Deployment 不因 UI 简化而合并语义。
10. 薄纵向验证：先用 Golden Path 证明独特价值，再横向补全各模块。

## 初期非目标

- 不自研音视频会议系统；
- 不自研 Git 代码托管；
- 不在早期建设大型插件市场；
- 不同时开发 Web、移动端和 PC 客户端；
- 不为了插件化把所有业务拆成独立进程；
- 不追求完整替代大型项目组合管理、财务或 ERP 产品；
- 不默认对所有消息启用会破坏搜索、审计和机器人能力的端到端加密；
- 不在产品闭环尚未建立时引入大量微服务。
- 不在首期建设完整内部开发者门户、服务依赖图或战略项目组合管理。

## 成功判断

首个可用版本应能让一个真实研发团队完成以下闭环：

1. 在频道讨论需求并形成可确认、可替代的 Decision；
2. 从 Decision 建立工单，不复制和丢失原始讨论；
3. 在文档中记录设计并关联 Decision、工单和 Component；
4. 由 Jenkins 插件将 Repository 构建映射为 CI Run；
5. 记录构建进入 Environment 的 Deployment，并保留审批与来源；
6. 从任意对象查看经过权限过滤的关系和时间线；
7. 在同一上下文中完成问题定位和交付复盘；
8. 在不依赖外部托管服务的情况下完成部署、升级、备份和恢复。
